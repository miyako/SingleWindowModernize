# シングルウィンドウアプリケーション

Thomas Maul（4D Germany）

テクニカルノート24-14

## 概要

本テクニカルノートでは、以前の4Dサンプルである4D Invoiceをもとに、従来のアプリケーションを最新のシングルウィンドウアプリへモダナイズする方法を紹介します。動的でユーザーがカスタマイズ可能なツールバー、ユーザーがカスタマイズ可能なリストボックス、そしてMicrosoft Outlookに似た表示とユーザー操作の仕組みを取り上げます。これにより、詳細情報を表示するためにダブルクリックする従来の操作を避け、同じウィンドウ内でデータを扱えるようになります。

## はじめに

従来のアプリケーションでは、出力フォームにデータの一覧を表示し、エンドユーザーがダブルクリックすると、新しいプロセスで実行される新しいウィンドウを開いて、レコードの詳細を表示することがよくあります。

新しいウィンドウを開くたびにプロセスを作成すると、大規模なネットワークでの負荷が増加します。特に、在宅勤務などで利用する低速なネットワークでは、パフォーマンスに大きく影響します。

ユーザー体験をシングルウィンドウ方式へ変えるために、エンドユーザーがカスタマイズできるリボン形式のツールバーの追加、出力フォームを置き換えるリストボックス、ダブルクリックによる詳細表示を置き換えるプレビューエリアなど、いくつかの手順を紹介します。これらはモダナイズの進め方の一例にすぎません。アプリケーションを改善する際には、すべてを取り入れても、一部だけを取り入れてもかまいません。

理解しやすいよう、本テクニカルノートの内容を次の3部に分けます：

- ツールバー
- リストボックス
- プレビューエリア

## 最低要件

この仕組み全体はクラスを基盤としているため、アプリケーションはプロジェクトモードである必要があります。本テクニカルノートのソースとサンプルコードは、4D 20 R2～R5で追加された言語機能を利用しています。

ツールバーのサンプルについて、古い4Dバージョンを使用する必要がある場合は、https://github.com/ThomasMaul/Toolbar にある以前のバージョンのツールバークラスを利用できます。こちらは4D 18 R3以降が必要です。主な機能は同じです。

## サンプルアプリケーションについて

4D Invoiceは20年以上前に公開され、さまざまなバージョンがリリースされてきました。標準サンプルとして、またオブジェクトフィールドをカスタムフィールドとして使用するなど、新機能の紹介にも利用されてきました。最新の公開版は、ORDAの機能を紹介するために全面的に書き直されたものです。このサンプルは、複数の4D Tourイベントでも使用されました。

本テクニカルノートでは、書き直す範囲を最小限に抑えながら従来のアプリケーションをモダナイズする方法を紹介するため、4D 16をベースとした以前のバージョンの4D Invoiceをサンプルの土台に選びました。

サンプルの最新バージョンは、次の場所から入手できます：

https://github.com/ThomasMaul/EA_Invoices/tree/SingleWindowMode

## 第1部：ツールバーとリボンバー

特にWindowsのSDI（Single Document Interface）アプリケーションでは、メニューバーを使うのではなく、リボンやツールバーを中心に操作します。

この部では、ウィンドウのサイズ変更に対応し、エンドユーザーが必要に応じて機能を選択・配置できる動的なツールバーの実装方法を紹介します。

アプリケーションに、利用可能な幅に応じてサイズを変更するボタンツールバーを追加するには、処理を担当する2つのクラスを追加するだけです。十分なスペースがあればタイトル付きの大きなボタンを表示し、スペースが狭くなるとタイトルを省略して小さくします。省略したタイトルはツールチップとして表示します。さらに、小さいアイコンを使い、2つのボタンを上下に重ねて表示することもあります。

このクラスは、通常のボタン、代替アクションを持つボタン（ボタンの横の矢印でコンテキストメニューを開きます）、および検索ピッカーを表示するサブフォームに対応しています。

## ツールバー設定：エンドユーザーによる設定

設定ダイアログでは、エンドユーザーが表示するボタンを選択し、その位置を変更したり、サブグループのボタンをメインのボタンへ移動したりできます。

サンプルデータベースで「Settings」ボタンをクリックし、続いて「Toolbar Setup」を選択すると、次のダイアログが開きます：

![](fig-05)

左側には利用可能なすべてのボタンや機能が表示され、右側には現在ユーザーが選択しているものが表示されます。右側でボタンを別の位置へドラッグ＆ドロップしたり、右クリックで削除したりしてみてください。「Reset」をクリックすれば、いつでも既定の構成に戻せます。

左右を比較すると、既定の構成には、最上位の「All」ボタンと、その下にある「All」「Selected」「None」のサブボタン（コンテキストメニュー）から成るグループが含まれていることがわかります。ツールバーでは、これを矢印付きのボタンとして表示します。矢印をクリックすると、追加の3つのボタンを含むサブメニューが開きます。エンドユーザーは、よく使う操作のサブボタンを最上位へ移動するなど、配置を変更できます。

エンドユーザーからのサポート問い合わせを減らすため、コードでは、ボタンが不適切なグループへ移動されたり、重複して存在したりしないようにチェックしています。

ツールバー設定ダイアログは、ツールバーの動作に必須ではありません。開発者、顧客側の管理者、エンドユーザーによるカスタマイズに役立ちますが、希望や要件に応じて、すべてをコードで処理することもできます。

### ツールバー設定機能のインストール

アプリケーションに導入するには、主要な2つのクラスに加えて、「Toolbar_Setup」クラスと「Toolbar_Setup」プロジェクトフォームをコピーします。

「Toolbar_Setup」フォームでは、Resources/en.lproj/ToolbarEN.xlfに保存されているローカライズ済み文字列を使用しています。このファイルとフォルダーもコピーしてください。ドイツ語訳も用意されています。ほかの言語を追加するには、フォルダーを複製し、名前と内容を変更します。

### ツールバー設定の保存

開発者は、利用可能なすべてのボタンの一覧（ツールバー設定で利用し、左側に表示するもの）を含むファイルと、既定の設定一覧を含むファイルの2つを配布する必要があります。

ファイルはResources/Settings/Toolbar/Buttons.jsonとDefault.jsonです。

エンドユーザーが一覧を変更して保存すると、設定はLogs/Setup/Toolbar/User.jsonに保存されます。

注：シングルユーザーモードでは、Logsフォルダーはデータファイルの隣にあります。クライアント/サーバーモードでは、現在のユーザーフォルダー内にあり、その場所はOSによって異なります。

Default.jsonファイルを作成するには、このダイアログでボタンを希望どおりに配置して保存し、User.jsonをDefault.jsonへ名前変更して利用すると便利です。両者の形式は同じです。

## ツールバーの初期化：コードを使用する場合

すべてをコードで行う場合は作業が増えますが、より細かく制御できます。

上記と同様にcs.Toolbarの新しいインスタンスを取得します。次に、各ボタンについてcs.Toolbar_Buttonのインスタンスを取得し、Form.toolbar.add($mybutton)でツールバーオブジェクトに追加します。

Toolbar_Buttonの新しいインスタンスを作成するときには、大きいアイコン、小さいアイコン、フォントサイズ、スタイル、タイトル、幅、ツールチップ、ポップアップの位置、コールバックメソッドなど、個々の要素を指定する必要があります（または指定できます）。

詳細は「ツールバーボタンのプロパティ」の節を参照してください。

## ツールバーのコールバック：クリックやイベントへの対応

コードでボタンを作成する場合は、ボタンがクリックされるたびに呼び出すコールバックメソッドを指定します。設定ダイアログを使用する場合、名前は「ORDA_Listbox_Method」としてハードコードされています。

このメソッドで、ボタンのクリックイベントを処理します。

メソッドは引数なしで呼び出され、オブジェクトメソッドとして動作します。そのため、最初にボタン名を取得し、どのボタンがクリックされたかに応じて処理できるようにします。

例：

```4d
var $buttonname : Text:=FORM Event.objectName
Alert($buttonname+” was clicked”)
```

注：FORM Eventは、On Clickedなどのイベントの種類を示すcodeプロパティを常に返すほか、状況に応じて多くのプロパティを返します。objectNameはさまざまな場面で役立つ情報です。特にリストボックスでは、まだ詳しく確認したことがなければ、ドキュメントを参照することをおすすめします（https://developer.4d.com/docs/FormObjects/listboxOverview/#supported-form-events-1）。

サンプルアプリケーション4D Invoicesでは、ORDA_Listbox_Methodコールバックメソッドを複数のイベントに使用しています。ツールバーボタンのイベントだけでなく、リストボックスのサイズ変更やダブルクリックにも使用しています。参考として、中身を確認してみてください。

ボタンのクリックについては、リストボックスクラスの関数に処理を転送します：

```4d
var $buttonname : Text:=FORM Event.objectName
CALL FORM(Current form window; Formula(Form.ORDA_listbox.handleButtonClick($buttonname; $event)))
```

このクラス関数はCase ofでAll、None、Selected、Query、Sort、Printなどの標準ボタンを調べ、それらの操作に共通の処理を提供します。それ以外の、アプリケーション固有の名前の場合は、ボタン名とともに「customButton」という引数を渡してODA_Listbox_methodを再び呼び出し、より個別の処理を実行できるようにします。

共通処理では、全レコードの選択やウィンドウタイトルの更新（5件中5件）などの基本的な作業を行います。

では、特定のテーブルで異なる動作が必要な場合はどうすればよいでしょうか。

button = “all”の場合のコードを確認してください。This.useAll($classname)を呼び出しています。

```4d
Function useAll($class : 4D.DataClass)->$all : 4D.EntitySelection
If ($class.useAll#Null)
    $all:=$class.useAll()
Else
    $all:=$class.all()
End if
```

少し変わった書き方に見えるかもしれませんが、考え方は単純です。指定されたテーブルまたはクラスに「useAll」というクラス関数があるかどうかを調べます。あればそのメソッドを呼び出し、なければ標準の.all()関数を呼び出します。

たとえば、useAll(ds.CLIENTS)を呼び出すとします。

CLIENTSに「useAll」というデータクラスの関数が定義されていれば、それを実行します。なければ、単にds.CLIENTS.all()を実行します。

このように、すべてのテーブルで使える汎用的なall関数を用意しつつ、一部のテーブルに専用のall関数を追加するだけで、動作を上書きできます。

サンプルアプリケーションのCLIENTSクラスには、次のように記述されています：

```4d
Function useAll()->$all : cs.CLIENTSSelection
$all:=ds.CLIENTS.all().orderBy("Name asc")
```

CLIENTSの表示中にこのボタンをクリックすると、この関数が実行され、結果が自動的にソートされます。請求書では未払いのものだけ、注文では未出荷のものだけを表示する、といった使い方も考えられます。

この仕組みにより、共通の動作を持たせながら、必要に応じてテーブルごとに上書きできます。長いCase ofを書く代わりに、テーブル固有のコードをそのテーブルに直接置きます。allやqueryなどの機能ごとに、すべてのテーブルの例外を長いCase ofで処理するか、例外を各テーブルに直接記述するかは、開発の進め方の問題です。ここでは、新しいクラス関数の利点を活用する方法として、この仕組みを紹介しています。

## ツールバーの検索ボックス

Toolbarクラスでは、ツールバーの右側に検索ボックスを追加できます。

設定ダイアログとリストボックスクラスを組み合わせて使用すると、現在表示しているテーブルに「quickSearch」というクラス関数があるかどうかに応じて、検索ボックスが自動的に表示または非表示になります。

CLIENTSクラスの例：

```4d
Function quickSearch($value : Text)->$all : cs.CLIENTSSelection
If (Length($value)<3)
    $all:=This.useAll()
Else
    $all:=This.query("Name=:1 or Email=:2 or City=:1 order by Name asc"; $value+"@"; "@"+$value+"@")
End if
```

このウィンドウで顧客を表示すると、ツールバーに検索ボックスが表示されます。プロジェクトへ切り替えると、ProjectsクラスにはquickSearch関数がないため、検索ボックスは非表示になります。

設定ダイアログ経由でToolbarを使用すると、ORDA_Listbox_Methodがコールバックとして指定されます。このメソッドでは、クリックまたはOn Data Changeイベントを調べます：

```4d
: ($event=On Data Change)
    If (String(FORM Event.objectName)="search")
            CALL FORM(Current form window; Formula(Form.ORDA_listbox.handleSearchbox()))
    End if
```

handleSearchbox()はORDA_Listboxクラスの関数です。現在のテーブルにquickSearch関数があるかどうかを調べ、あれば実行します。

ツールバーを自分で初期化する場合は、ボタンを追加するときに、コードで検索ボックスも追加してください。

```4d
var $searchbox : cs.Toolbar_Button:=cs.Toolbar_Button.new(New object("name"; "search"; "group"; "300";
"mytype"; 1; "prio"; 1000))
$searchbox.width:=205
$searchbox.height:=36
$searchbox.method:="mycallback"
$searchbox.subform:="SearchPicker"
C_TEXT(vSearch)
$searchbox.dataSource:="vSearch"  // needs to be a process text variable, Form.xx will not work
$searchbox.dataSourceTypeHint:="text"
vSearch:=""  // default text empty
Form.toolbar.add($searchbox)
```

上の例では、ツールボックスにあるSearchPickerウィジェット（https://doc.4d.com/4Dv20R6/4D/20-R6/Overview.300-7185320.en.html）を使用し、「mycallback」をオブジェクトメソッドとして指定しています。

このメソッドでOn Data Changeを調べ、検索など、必要な処理を行います。

## ツールバーボタンのプロパティ

ツールバーで必要なボタンごとに、新しいインスタンスを作成します。コンストラクターのnew.()では、ボタンのほぼすべてのプロパティを渡せます。

**mytype**
0はボタン、1はサブフォームまたはコンテナーです。4Dの標準オブジェクトプロパティではありません。

**title**
ボタンのテキストです。

**name**
オブジェクト名です。イベントメソッド内で利用できます（OBJECT Get name(Object current)を使用します）。

**prio**
どのボタンを先に縮小するかを決める優先度です。大きい値から先に縮小し、小さい値は最後に縮小します。4Dの標準オブジェクトプロパティではありません。

**group (text)**
グループが変わる位置に、ボタンを区切る縦線を表示します。4Dの標準オブジェクトプロパティではありません。

**icon**
4ステートボタン用の32x32のPNG画像への4D相対パスです。例：/RESOURCES/Images/ButtonNew32.png

**icon16**
4ステートボタン用の16x16のPNG画像への4D相対パスです。例：/RESOURCES/Images/ButtonNew16.png。4Dの標準オブジェクトプロパティではありません。

**tooltip**
ツールチップのテキストです。指定しなければ、ボタンのタイトルを使用します。

**width**
ボタンまたはサブフォームの幅です。既定値は70です。

**height**
ボタンまたはサブフォームの高さです。ボタンの既定値は55で、小さいボタンでは自動的に30へ縮小します。

**popupPlacement**
空、または"separated"を指定します。"separated"にすると、右クリック操作用の矢印を追加します。この場合は通常、ボタンの幅を広げる必要があります。"onAlternateClick"イベントの追加も忘れないでください。

**events (collection)**
指定したメソッドを呼び出すイベントのコレクションです。ほとんどの場合は"onClick"が必要で、右クリックには"onAlternateClick"も必要です。

**style**
CSSスタイル名です。

**method**
イベント時に呼び出すメソッドです。プロジェクトメソッドの名前を渡します。

**subform**
type=1の場合のみ使用します。表示するサブフォーム名（例："SearchPicker"）です。

**dataSource**
type=1、つまりサブフォームの場合のみ使用します。データソースを指定します。SearchPickerでは、プロセステキスト変数である必要があり、Form.xxxは使用できません。

**dataSourceTypeHint**
dataSourceの型です。SearchPickerでは"text"を渡します。

ツールバーを使用するだけであれば、これらのメソッドを自分で呼び出す必要はありません。機能を拡張または書き直す場合にのみ使用してください。

## 第2部：カスタマイズ可能なリストボックス

アプリケーションにカスタマイズ可能なリストボックスを追加するには、すべての処理を行う1つのクラスと、列を指定していない空のリストボックスをフォームに追加するだけです。表示するテーブルと、列に表示する式は、実行時に動的に指定されます。

付属のサンプルアプリケーション4D Invoiceでは、左側の一覧表示と右側のプレビューエリアの間にあるスプリッターを移動すると、リストボックスの幅を変更できます：

サイズを変更すると、次のようになります：

![](fig-08)

エンドユーザーは列を右クリックして、列を追加または削除できます：

![](fig-09)

表示するフィールドの一覧には、「実際の」フィールドだけでなく、エイリアス（通常はリレート先テーブルのフィールド）や計算属性も含まれます。

## インストール

請求書サンプルアプリケーションから「ORDA_Listbox」クラスをコピーします。また、ダブルクリック処理などのコールバック処理に使われる「ORDA_Listbox_method」プロジェクトメソッドもコピーします。これをサンプルとして、必要なコードを取り出せます。ツールバークラスも使う場合は、このメソッドの大部分を出発点にするとよいでしょう。

次に、プロジェクトフォームとリストボックスオブジェクトを作成します。

リストボックスオブジェクトでは、次のプロパティを設定します：

![](fig-10)

ソースにForm.listboxを指定し、データソースとしてForm.SelectedElement、Form.SelectedPosition、Form.Selectionを設定します。最後の3つは、本シリーズの第3部で説明するプレビューエリアと組み合わせる場合にのみ必要です。

フォームメソッドには、On Loadイベントの処理として次を追加します：

```4d
Form.ORDA_listbox:=cs.ORDA_Listbox.new(ds.CLIENTS)  // adapt to your default table to start with
Form.ORDA_listbox.load()
Form.ORDA_listbox.setInputForm()
```

On Resizeイベントの処理も追加します：

```4d
: (Form event code=On Resize)
    Form.ORDA_listbox.resize()
```

サンプル4D InvoicesのプロジェクトフォームORDAListboxと、そのフォームメソッドを参考にしてください。

最後に、ヘッダーの右クリックと、必要に応じて行のダブルクリックを処理する、リストボックスのオブジェクトメソッドが必要です。

サンプル4D Invoiceのオブジェクトメソッド（ORDAListboxフォームのListboxオブジェクト）を開いてください。変更せず、そのまま利用できます。

最初の部分はヘッダーの右クリックを処理しており、おそらくそのまま利用することになるでしょう。On Selection Changeイベントの部分は、プレビューエリア（本テクニカルノートシリーズの第3部）も使用する場合にのみ必要です。On Double Clickedイベントの部分は、そのまま利用しても、ダブルクリック時の動作に合わせて書き直してもかまいません。

## 第3部：プレビューモード

多くのビジネスアプリケーションでは、レコード一覧を表示し、ダブルクリックすると編集用の新しいウィンドウを開きます。シングルウィンドウアプリケーションでは、レコードを1回クリックするだけで、プレビューエリアに詳細を直接表示します。エンドユーザーは、一覧のレコードをすばやく参照し、クリックして詳細を確認できます。変更を加えた後で別のレコードをクリックすると、変更を保存するかどうかを尋ねるダイアログを表示します。楽観的ロックを使うため、この仕組みは非常に効率的です。

レコードをダブルクリックすると新しいウィンドウが開き、複数のウィンドウを利用することもできます。

多くのエンドユーザーは、Microsoft Outlookでこの操作方法に慣れているため、業務の現場にも導入しやすくなります。

## On Selection Change

On Selection Changeイベントが、この仕組みの中心となります。フォームを開いたとき（要素が選択されていない状態）と、ユーザーがレコードをクリックしたり、別のレコードを表示したりして選択が変わるたびに呼び出されます。

ここで重要なのは、現在のレコードだけでなく、直前に選択していたレコードにも注意することです。理由を問わず選択が変わったら、直前に選択していたレコードが変更されていないかを確認し、変更を保存するかどうかユーザーに尋ねる必要があります。

そこで、選択変更イベントが発生したら、直前に選択していたレコードがあるかどうかを調べます。あれば、それが変更されているかを確認します。変更されていれば、保存するかどうかをユーザーに尋ねます。保存する場合は、自動マージオプションで保存を試みます。失敗したら、たとえば待機するかどうかなど、次の操作を尋ねます。待機する場合は、直前に選択していた位置を再選択する必要があるため、その位置も保存しておきます。

いずれの場合も、現在の要素と位置を記憶し、サブフォーム内で表示データを初期化するメソッドを実行する必要があります。請求書サンプルでは、顧客データの表示時にカスタムデータのリストボックスの表示・非表示を切り替え、請求書では、一部のフィールドの入力可否を設定します。従来のアプリケーションでは、変数に表示するデータを計算することがよくありますが、より新しいアプリケーションでは、式として変数に直接設定したり、計算属性を使用したりします。

ここで示すコードは、独自の開発に向けたサンプルや土台としてのものです。

```4d
: ($event.code=On Selection Change)
   If (Form.preview.data#Null)
      If (Form.preview.data.touched())
         C_COLLECTION($touchedAttributes)
         $touchedAttributes:=Form.preview.data.touchedAttributes()
         var $check : Boolean:=True

         If ($check)
            CONFIRM(Get localized string("SaveChanges"))
            If (OK=1)
               C_OBJECT($status)
               $status:=Form.preview.data.save(dk auto merge)
               Case of
                  : ($status.success)
                     // nothing all fine
                  : ($status.status=dk status automerge failed)
                     ALERT(Get localized string("SomebodyElseChanged"))
                  : ($status.status=dk status locked)
                        var $user : Text:=$status.lockInfo.user_name+"/"+
                           $status.lockInfo.host_name+"/"+$status.lockInfo.task_name
                        CONFIRM(Get localized string("RecordLockedFrom")+$user;
                           Get localized string("LockedWait");
                           Get localized string("LockedCancel"))
                        If (OK=1)
                           LISTBOX SELECT ROW(*; "Listbox"; Num(Form.preview.Position);
                              lk replace selection)
                           Form.SelectedElement:=Form.preview.data
                        Else
                        End if
                  End case
               End if
            End if
         End if
      End if
      Form.preview.data:=Form.SelectedElement
      Form.preview.Position:=Form.SelectedPosition
      EXECUTE METHOD IN SUBFORM("preview"; Formula(ORDA_Listbox_Method("preview")))
```

注：正しいフォームコンテキストで実行するために、初期化コードはEXECUTE METHOD IN SUBFORMで実行することが重要です。

## On Double Clicked

サンプルアプリケーションでは、On Double Clickedイベントで新しいプロセスを開き、クラシック言語でレコードを変更します。これはクラシックを推奨するためではなく、既存のクラシックアプリケーションを、すべて書き直すことなくORDAでモダナイズする方法を示す例です。メインウィンドウは通常、エンドユーザーの作業の大部分を担い、必要な書き直しはわずかです。もちろん、新規開発やリファクタリングでは、入力フォームもORDAへ書き直すことをおすすめします。

## 書き直しがユーザーにもたらす利点

アプリケーションの書き直しには、多くの作業が必要です。そこで大切なのは、なぜ書き直すのか、どのような利点があるのかという問いです。

最もわかりやすい理由は、インターフェースのモダナイズです。SDIアプリケーション、シングルウィンドウ方式、Outlookのような操作感、あるいは単にWebアプリケーションで慣れているインターフェースにすることです。Webアプリケーションでは、レコードを変更するのに1回クリックする操作に慣れているため、ダブルクリックは不自然に感じられます。

これはユーザー体験につながります。ユーザーは、目で確認しながらレコードを探すことがよくあります。検索機能でレコードを絞り込んだ後、対象のユーザーや請求書を特定できず、詳細を確認するために順にクリックしていきます。

従来の方式では、レコードをダブルクリックして確認し、ウィンドウを閉じて次をダブルクリックします。これはユーザーにとっても、システムにとっても効率的ではありません。新しいプロセスの開始と終了だけで、多くの通信とサーバー負荷が発生します。シングルウィンドウで一覧を順に参照できれば、この作業を大幅に高速化できます。

3つ目の理由は、ネットワークトラフィックとサーバー負荷の削減です。多くのユーザーがいる大企業では、特に効果が大きくなります。在宅勤務など、リモートで働くことが多い現在、ネットワークトラフィックの削減は重要です。インターネット回線は年々高速化していますが、ネットワークパケットがサーバーに届いて応答を受け取るまでのレイテンシーは、直接のEthernet接続に比べて100倍ほど長くなることがよくあります。

2つの方法を比較するため、Clients_Manageメソッドを実行して従来の方法で開き、すべてのネットワーク操作を記録します。次に、Start_ORDAWindowを実行して新しい方法で開き、同様に記録します。

4D Serverを起動し、同じコンピューター上で動作する4Dからリモート接続します。サーバーのメンテナンスウィンドウで、メソッドの実行前にリクエストログの記録を開始します。

後は、in/outのバイト数を合計し、パケット数を数えれば、両方の方法を直接比較できます。

どちらも顧客一覧を表示します。従来のモードでは、3つのレコードをそれぞれダブルクリックして開き、閉じる操作を繰り返します。ORDAモードでは、1回クリックするだけでプレビューに表示します。

ログファイル4DRequestsLogServer_1.txtには、転送された各パケットと、そのin/outのバイト数が記録されます。

従来のモードでは、outが11kbyte、inが14kbyteで、124パケットを使用します。

ORDAモードでは、outが92kbyte、inが6kbyteで、50パケットを使用します。

ここで、なぜORDAの方がバイト数が多いのか、少なくなるはずではないのかという疑問が生じます。ORDAはデータをまとめ、1つのパケットでより多くのデータを送信することで、低速なネットワークを高速化しようとします。インターネット経由でも通常、帯域幅は十分にあるため、多くのデータを送れます。一方で、1つのパケットを送るのには時間がかかります。

そこで、最初のレコード群を要求すると、ORDAは表示される量よりも大きいデータのまとまりを先に送り、ローカルキャッシュとして扱います。これにより、特に低速なネットワークで、通信処理が大幅に高速化します。

この動作は簡単に確認できます。同じログフォルダーにあるORDARequests_1.jsonには、ORDAの各パケットが内容も含めて記録されています。どのリクエストに対して、どの応答が返されたかを確認できます。

データをまとめることで、やり取りするパケットが減ります。クリックやダブルクリックを繰り返すほど、その差は大きくなり、ORDAの方が有利になります。

ORDARequests.jsonログファイルを使えば、転送をさらに最適化できます。

次に例を示します：

## まとめ

モダンなユーザーインターフェースにとって、ボタンツールバーは重要な要素です。さまざまなモニターに対応し、ユーザーによるウィンドウのサイズ変更を可能にするために、画面の幅へ自動的に適応させると、ユーザー体験が向上します。エンドユーザーが自分の作業の流れに合わせてボタンツールバーを調整できれば、受け入れられやすくなり、満足度も高まります。ここで紹介したクラスを使うと、コードの制御を維持し、複雑なフレームワークに依存せずに、このようなツールバーをアプリケーションへ実装する作業を大幅に簡単にできます。

多くのアプリケーションで、リストボックスが中心的なユーザー操作の要素として使われています。しかし、表示するフィールドの選択、順序の変更、列の既定幅の変更といったカスタマイズ機能を備えていないことが少なくありません。汎用的なクラスでこれらの要件を自動化すると、アプリケーションの標準機能として、容易に提供できます。

出力ウィンドウと入力ウィンドウを行き来する方式からシングルウィンドウへ切り替えると、エンドユーザーの多くの作業を高速化できます。サーバー負荷を抑え、必要なネットワークリソースや通信のやり取りも減らせるため、モダナイズされたユーザーインターフェースに適した選択肢です。
